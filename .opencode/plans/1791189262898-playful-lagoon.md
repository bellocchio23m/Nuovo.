# Analisi tecnica — Action/stealth 3D sistemico nel browser (piattaforma OMGithub)

> Stato: ANALISI, nessun codice di gioco generato. Questa è la valutazione rigorosa richiesta prima di qualsiasi progettazione.

## 0. Sintesi in una riga

Il concept completo (80 NPC persistenti + emergenza + polizia non-onnisciente + 3D realistico) **non è realizzabile alla lettera** su questa piattaforma. Il **nucleo emergente** (verità-di-mondo vs. credenze-NPC vs. informazioni-polizia) **è invece realizzabile** se sacrifichiamo fotorealismo, fisica completa e numero di NPC simultaneamente dettagliati. Architettura obbligata: **simulazione autoritativa a tick fisso + LOD a 3 livelli + knowledge-graph separato dal ground-truth + rendering Three.js low-poly istanziato**.

## 1. Capacità effettive della piattaforma (verificate, non presunte)

Verificate leggendo il runtime reale (`RUNTIME_DIR/scripts/default-start.mjs`, `default-capture.mjs`, `gpu-capture.mjs`, `Agents.md`, config Playwright `~/.local/share/omgithub-playwright/linux.json`, Node v22.23.3):

- **Linguaggi:** JavaScript (Node 22 verificato). TypeScript solo se compilato via Vite in build statica. Nessun backend eseguibile in deploy: il server è un `node:http` statico che fa `readFileSync` per richiesta.
- **Tipi di progetto supportati:** solo `index.html` statico oppure progetto **Vite** (build in `dist/`). **Next.js esplicitamente rifiutato** dal runtime. Niente SSR, niente server custom, niente WebSocket server.
- **Rendering 3D:** Three.js (via CDN o bundle Vite) è la strada sanzionata — esiste apposita skill `load-sketchfab-threejs` (GLTFLoader, normalizzazione/validazione GLB). WebGL funziona. **WebGPU è abilitato ma solo via SwiftShader CPU** (`--use-vulkan=swiftshader --use-webgpu-adapter=swiftshader`). `Agents.md` impone di riportarlo come **software rendering CPU, mai come accelerazione GPU**.
- **WebAssembly:** servito (`mime .wasm` presente nel server). Usabile per fisica (Rapier) o pathfinding, ma aumenta peso e tempo di avvio.
- **Threading:** Web Workers disponibili (standard Chromium), ma niente SharedArrayBuffer garantito senza header COOP/COEP — e il server statico **non invia tali header** (solo `Cache-Control: no-cache`). Quindi parallelismo = Workers con messaggi, non memoria condivisa. Utile, ma con costo di serializzazione.
- **Salvataggio:** solo client-side: `localStorage` (sincrono, ~5 MB, da usare solo per metadati/slot) + **IndexedDB** (asincrono, decine di MB, sede reale dei salvataggi). Nessun filesystem, nessun cloud-save. Salvataggi = serializzazione JSON manuale e versionata.
- **Audio:** solo Web Audio / `<audio>`. Nessuna garanzia di asset esterni: o si sintetizza (oscillatori) o si incorporano file leggeri. **Autoplay bloccato fino a gesto utente** (policy Chromium) — il gioco deve partire da un click/tap.
- **Fisica:** nessuna fisica nativa. Va portata da JS/WASM (cannon-es, Rapier). Costo CPU interamente sul thread principale (o Worker).
- **Networking:** nessun server autoritativo possibile (deploy statico). Solo fetch outbound verso CDN pubbliche. **Multiplayer real-time = ROSSO** (al massimo WebRTC P2P con signaling esterno, fuori piattaforma). Gioco = single-player offline.
- **API browser:** pieno DOM/Canvas/WebGL/Input/Gamepad standard. Niente accesso a file system, niente notifiche push affidabili, niente background processing a tab chiusa.
- **Limiti specifici verificati del server statico:**
  - MIME serviti: `.html .js .css .json .svg .png .jpg .webp .wasm .glb`. Altro (es. `.woff2`, `.mp3`, `.ogg`) cade in `application/octet-stream` → rischio asset che non caricano o warning CORS/MIME. Tenere i font di sistema o incorporare in base64/CSS.
  - Nessuna compressione (gzip/brotli), nessuna cache (`no-cache`/`no-store`): **ogni MB pesa sul caricamento iniziale**.
  - Validazione automatica con screenshot desktop (1440×900) + mobile (390×844): canvas vuoto, schermata di caricamento infinita o assenza di geometria = rigetto (`analysePixels` richiede varianza cromatica interna). Il gioco deve mostrare **geometria reale entro pochi secondi**, con `pageerror` loggati.
  - Sicurezza path: solo file dentro la root, niente traversal.

## 2. Limiti reali (colli di bottiglia probabili)

- **80 NPC, IA per-frame:** budget a 60 fps = 16,6 ms/frame totali. Un agente "completo" (percezione conica + LOS + decisioni + memoria) costa ~0,1–0,3 ms in JS ottimizzato → 80 agenti = 8–24 ms, **cioè da solo oltre il budget, prima ancora di rendering e fisica**. 80 agenti completi ogni frame = impossibile. Obbligatorio time-slicing + LOD (vedi §5).
- **Pathfinding:** A* su griglia piccola (es. 100×100 celle) è economico se scaglionato (pochi ricalcoli/frame) e con path condivisi/caching. Collo: 80 ricalcoli simultanei + avoidance dinamica → picchi. Soluzione: path ricalcolati a eventi (non ogni frame), code con priorità, steering solo per i vicini.
- **Fisica:** corpi cinematici + trigger = economico. Rigid-body completo con collisioni a catena = costoso e imprevedibile su CPU SwiftShader/mobile. La fisica è il primo sistema da confinare a "volumi di affordance".
- **Rendering:** il vincolo non è il numero di triangoli in sé ma **draw call e stato**. 80 NPC come 80 mesh skinned separate = collo certo. Via d'uscita: low-poly + `InstancedMesh`/materiali condivisi + LOD + niente ombre dinamiche ad alta risoluzione (o una sola luce con shadowmap piccola). Fotorealismo con PBR pesante + ombre + post-processing su SwiftShader = slideshow nella validazione.
- **Memoria:** tab Chromium tipica 1–2 GB, ma su mobile molto meno e con kill aggressivi. 80 schede NPC come dati = pochi KB (irrilevante). Il peso sta in geometrie/texture/audio non compressi via rete (vedi server senza gzip). Target: **payload iniziale < 10–15 MB**, texture compresse/poche, audio sintetizzato.
- **CPU/GPU:** la validazione gira su **CPU (SwiftShader)**; l'utente finale su GPU mista (integrata/mobile). Progettare per il caso peggiore: logica < 3–4 ms/frame, rendering low-poly 30 fps su SwiftShader come soglia minima.
- **Salvataggi:** serializzare 80 NPC + relazioni + journal eventi è piccolo (< 1 MB JSON) se i dati sono numerici/simbolici, non geometrici. Collo: salvare stato fisico continuo (posizioni/velocità esatte di tutto) + screenshot → gonfia e fragilizza. Salvare **stato simbolico + snapshot compatto**, mai dump cieco.
- **Dimensione/caricamento:** senza compressione server, ogni libreria (three.js ~600 KB min, Rapier WASM ~1–2 MB, audio) si paga. Import via CDN = dipendenza di rete in fase di validazione (flaky). Preferire bundle Vite autoritativo e self-contained.
- **Mobile:** 390×844 con touch, thermal throttling, niente hover, mira/comandi stealth imprecisi. Parità desktop/mobile con stessa fedeltà = irrealistico. Mobile = esperienza degradata dichiarata (LOD più aggressivo, UI touch semplificata).

## 4. Architettura consigliata

Principio: **separare ground-truth (cosa è successo) da credenze (chi sa cosa)**. Tutta l'emergenza nasce da lì.

- **World Sim autoritativa, single-thread, tick fisso (es. 10–20 Hz logica, rendering disaccoppiato).** RNG seedato per determinismo e debug. Nessuna autorità di rete (single-player).
- **Event Bus + Journal:** ogni fatto rilevante è un evento tipizzato `{t, tipo, dove, chi, cosa, testimoni[]}`. Il journal è la base di: memoria NPC, indagini polizia, persistenza, salvataggi. Mai cancellare: si compatta (sintesi) ma non si riscrive.
- **Knowledge layer (il cuore):** per ogni NPC/polizia, store di **credenze** `{fatto, confidenza 0–1, fonte, età}`. Percezione e voci scrivono credenze, mai ground-truth. Errori = rumore di percezione; menzogne = scrittura intenzionale di credenze false con tracciamento fonte (così si può scoprire il bugiardo incrociando fonti).
- **Scheduler NPC a budget fisso:** time-slicing con priorità (distanza dal giocatore, coinvolgimento in eventi, allarmi attivi). Budget IA/frame fisso (es. ≤2 ms): chi non rientra slitta. Decisioni come **utility scoring** su pochi bisogni (fame/lavoro/paura/curiosità) + stato credenze, non planning simbolico pesante.
- **Percezione a due velocità:** L1 (vicini, ≤ ~12 agenti): cono visivo + raycast occlusione contro collider semplificati + modello rumore; L2/L3 (altri): test probabilistico astratto (zona, ora, affollamento) senza raycast. Testimoni = chi supera la soglia scrive evento nel journal + credenza.
- **Routine come timeline simbolica:** ogni NPC ha agenda (casa→lavoro→bar→casa) su nodi della mappa, non coordinate continue. L3 avanza l'agenda senza muovere mesh; L2 interpola su grafo di waypoint; L1 muove il corpo con steering. Transizione L3→L1 consentita solo off-screen dal giocatore.
- **Navigazione:** grafo di waypoint/nodi + griglia di collisione baked per interni/esterni; A* scaglionato con cache; avoidance solo L1 e solo tra vicini.
- **Fisica:** mondo statico con collider semplici + agenti cinematici + **affordance-volume** (oggetti interagibili come nodi con stati: `avvelenabile, sabotabile, distraente, rumoroso`). Niente stacking fisico generalizzato.
- **Rendering:** Three.js, scena unica, materiali condivisi, `InstancedMesh` per pedoni/props ripetuti, 1 luce direzionale + emisferica, ombre piccole o finte (blob), LOD mesh per distanza, frustum culling nativo, niente post-processing in MVP. Stile low-poly dichiarato (non fotorealismo).
- **Mappa/streaming:** quartiere piccolo (~100–150 m lato) caricato intero; "streaming" = attivazione LOD e interni come nodi (porte = transizioni simboliche, non necessariamente interni modellati tutti). 8–12 edifici-nodo, 2–3 interni visitabili reali in MVP.
- **Stato globale:** store centrale immutabile-per-evento (snapshot + journal). Salvataggio = `{versione, seed, tempo, snapshot simbolico compatto, journal compattato}` in IndexedDB; metadati slot in localStorage.
- **Audio:** WebAudio sintetizzato (passi, allarmi, voci come blip/bark testuali brevi). Copertura sonora = meccanica a zone, non DSP fisico.

## 5. Come simulare 80 NPC senza 80 agenti completi per frame

Matematica di base (§2) → soluzione obbligata: **pochi cervelli accesi, tutti i corpi anagrafati**.

1. **Classificazione dinamica per frame:** L1 = entro raggio dal giocatore (cap ~10–12): tick completo (sensi, steering, animazione, interazioni). L2 = nel quartiere ma lontano: tick comportamentale a 1–5 Hz scaglionato (avanza agenda, decisioni semplici, niente raycast né animazione facciale). L3 = fuori scena/irrilevante: solo avanzamento simbolico quando serve (es. "alle 18:00 è al bar") calcolato on-demand, non per frame.
2. **Budget fisso:** scheduler che misura ms spesi e rimanda il resto al frame successivo. Mai fame: priorità a chi è coinvolto in eventi/allarmi.
3. **Percezione solo L1 + sensori statici (telecamere):** gli altri "sanno" solo via voci/eventi astratti. Questo è anche ciò che rende la polizia non-onnisciente senza costo extra.
4. **Regole di continuità anti-incoerenza:** (a) mai cambiare livello di un NPC visibile; (b) isteresi sul raggio (entra a 40 m, esce a 55 m); (c) L3→L1 materializza solo in punti di spawn non osservati (uscite edifici, bordi); (d) testimoni di eventi gravi marcati "pinned": non scendono mai a L3 finché l'evento è caldo.
5. **Conoscenze come grafo sparso:** non matrice 80×80 aggiornata sempre; solo archi toccati da eventi (incontri, voci, relazioni). La diffusione voci è un contagio limitato (pochi hop/giorno di gioco, con perdita di fedeltà) — produce incompletezza ed errori quasi gratis.
6. **Costo stimato:** L1 10 agenti × 0,2 ms = 2 ms; L2 30 agenti a 2 Hz ≈ 1–2 agenti/frame ≈ 0,3 ms; L3 ≈ 0. Totale IA ≈ 2–3 ms/frame. Compatibile con 30–60 fps logici.

## 6. Cosa sacrificare (senza toccare il nucleo emergente)

Il nucleo da proteggere: **ground-truth vs credenze, testimoni, polizia evidence-driven, conseguenze persistenti**. Tutto il resto è negoziabile:

1. **Fotorealismo → stilizzato low-poly "credibile".** Perdi fedeltà visiva, tieni leggibilità stealth (coni, coperture, stati d'allarme devono leggersi a colpo d'occhio meglio che col fotorealismo).
2. **Fisica generalista → affordance chiuse ma combinabili.** Non "ogni oggetto fa tutto", ma ~10–15 verbi-oggetto (avvelena, sabota, distrai, attira, blocca, registra…) che combinandosi danno decine di approcci. È qui che nasce l'emergenza a costo noto.
3. **Dialoghi/voice acting → barks + scambio astratto di conoscenze.** Le informazioni viaggiano come fatti (chi/cosa/dove/confidenza), mostrati con testi brevi. Niente alberi di dialogo ramificati nel MVP.
4. **Città → isolato.** Un blocco con 8–12 edifici-nodo e 2–3 interni reali dà più densità sistemica per MB di una città vuota. La "piccolezza" richiesta è un vantaggio tecnico: dichiara ~120×120 m e densifica.
5. **Ciclo giorno/notte continuo → fasce orarie a blocchi** (mattina/pomeriggio/sera/notte) che guidano le agende. Meno shader/illuminazione variabile, stesse opportunità stealth.
6. **80 NPC subito → 80 anagrafi, 12–20 simulati.** Il numero 80 resta come registro persistente; il costo vivo è capped. Scalare il cap è la roadmap, non il giorno uno.
7. **Mobile parity → mobile degradato dichiarato.** Stesso gioco, LOD più aggressivo, niente ombre, controlli touch semplificati.
8. **Incertezze dichiarate:** throughput WebGPU-SwiftShader reale misurabile solo col prototipo; quota IndexedDB variabile per browser; flakiness CDN (mitigare con bundle self-contained); tuning del "tasso di voci/errori" (troppo rumore = caos illeggibile, troppo poco = mondo morto) — è un parametro di game-design, non risolvibile a priori.

## 7. MVP (prototipo minimo ma realmente giocabile)

Obiettivo: **dimostrare il loop emergente**, non la scala. Una sola domanda da rispondere: *"un'azione non scriptata del giocatore (es. attirare il bersaglio in un luogo isolato avvelenandogli la bevanda dopo averne appreso la routine seguendolo) riesce o fallisce in base a chi ha visto cosa, e la polizia reagisce solo in base a ciò che sa?"*

- **Quartiere:** un isolato ~100×100 m, 6–8 edifici-nodo, 1 bar interno visitabile + 1 vicolo + 1 piazza. Porte/trigger, niente interni superflui.
- **NPC:** 12 (1 bersaglio + 2 con routine legata al bersaglio + 1 barista-fonte + 2 poliziotti + 6 passanti con agende semplici). Altri 68 come voci/anagrafe non spawnate (placeholder dati).
- **Sistemi dentro:** agende a fasce; percezione L1 (coni+rumore+testimoni); knowledge-graph con confidenza/fonte; polizia evidence-driven (insospettita/allerta/ricerca: pattuglie modificate, posti di blocco simbolici); 2+ vettori di uccisione combinabili (corpo a corpo isolato; veleno×bevanda×routine; distrazione×telecamera cieca); journal eventi + salvataggio IndexedDB + conseguenze (allerta persistente, NPC che evita zone, opportunità perse).
- **Astratto fuori:** L2/L3 solo agende; voci come testo; niente menzogne attive complesse (solo 1 NPC che può mentire alla polizia con regola semplice); niente ciclo giorno/notte continuo; audio sintetico minimo.
- **Obiettivo giocabile:** elimina il bersaglio senza farti identificare dalla polizia nella stessa sessione; il gioco mostra *cosa la polizia sa di te* (pannello evidenze) — è la prova dell'emergenza.
- **Criteri di successo (misurabili):** (1) uccisione "pulita" via routine+veleno con testimoni assenti → polizia resta a sospetto 0 dopo 5 min di gioco; (2) stessa azione con 1 testimone → allerta entro 60 s e pattuglie modificate; (3) reload da save mantiene cadavere/allerta/credenze; (4) ≥30 fps medi su capture desktop SwiftShader per 60 s con `pageerror` zero; (5) screenshot finale mostra scena 3D con geometria (criterio di validazione piattaforma).

## 8. Roadmap incrementale (ogni fase ha gate verificabili)

- **Prototype 0 — "Isolato che gira" (settimane 1–2):** Three.js + terza persona + colliders + 1 strada + 3 NPC dummy con waypoint + save/load. Gate: screenshot desktop+mobile con geometria, 30 fps SwiftShader, zero pageerror.
- **Prototype 1 — "Chi ha visto cosa" (= MVP §7):** 12 NPC + percezione + testimoni + polizia evidence-driven + 2 vettori kill + journal + pannello evidenze. Gate: i 5 criteri §7, di cui 2 dimostrano emergenza (stessa azione, esito diverso in base ai testimoni).
- **Prototype 2 — "Quartiere che ricorda":** 30 anagrafi (12 vive + 18 L2/L3), voci con perdita di fedeltà, 1 bugiardo, telecamere statiche, conseguenze a medio termine (zone evitate, sorveglianza alzata, opportunità perse/nuove). Gate: catena non scriptata di ≥3 hop (barista→conoscente→testimone→polizia) riproducibile da seed e visibile nel journal.
- **Alpha — "80 anagrafi":** 80 identità persistenti (cap vivi ~15), relazioni/fiducia, sabotaggi/distrazioni estesi (~12 affordance), 3 interni, fasce orarie complete, salvataggi multipli versionati. Gate: sessione 30 min senza degenerazioni (nessun NPC bloccato, nessun teletrasporto visibile, IA ≤3 ms/frame misurati).
- **Beta — "Gioco":** tuning emergenza (tasso voci/errori), UI/UX finale, audio sintetico completo, tutorial emergente (non scriptato: suggerimenti da osservazione), ottimizzazione mobile degradata, hardening save/migrazioni. Gate: playtest cieco — ≥1 giocatore su 3 trova una soluzione non prevista dai designer; crash-free su desktop+mobile capture.

### Vincoli operativi di questa piattaforma (promemoria per l'implementazione futura)

1. Build self-contained (Vite bundle, niente CDN runtime critiche); payload iniziale < ~15 MB; niente asset fuori MIME supportati.
2. Prima geometria visibile in < pochi secondi (validazione screenshot); schermata titolo con start su gesto utente (sblocca audio).
3. Determinismo seedato + journal ispezionabile: senza questi, l'emergenza non è debuggabile né dimostrabile.
4. Mai teletrasportare NPC visibili; mai conoscenza globale alla polizia (code review su ogni lettura di ground-truth dal sistema polizia).
